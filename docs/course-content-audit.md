# Java Spring Course Content Audit

## Executive Summary

This is a content-quality audit of all 40 authored teaching records in `content/lessons/`, scored against a 12-dimension rubric (A–L). No file in the course was modified; this document is the only artifact produced.

**The course has a strong theory corpus and a weak hands-on corpus, and the gap is the finding.**

| Record class | Count | Mean score (A–L) |
|---|---|---|
| Theory (`kind=theory`) | 20 | **4.23** |
| Hands-on (`kind=lab` / `project`) | 16 | **3.08** |
| Terminal (`exam` / `ojt` / `evaluation`) | 4 | **2.77** |
| **All records** | **40** | **3.62** |

The theory lessons are genuinely good: they teach mechanisms rather than definitions, argue rules from consequences, and reuse one mental model (the AOP proxy) across four lessons. Day 11, Day 26, Day 25, Day 13, Day 16 and Day 17 are publishable as-is with light edits.

The hands-on records are where the course breaks its promises. Nine consecutive records (Day 15 → Day 35) have no acceptance criteria and no rubric. Twelve required deliverables across seven records have **no artifact at all** — a `<template>` sentence or a `note` telling the learner to read the official docs. Five topics are *graded but never taught*: JaCoCo coverage, GitHub Actions CI, JPA `Specification`, `@Version`/pessimistic locking, and relational design (JOIN/index). The capstone's core business flow (Day 35 `checkout`) is three methods that return `null`.

Two defects are structural rather than per-lesson and drive most of the rubric losses:

1. **The no-cross-lesson-citation-borrowing rule is costing learner-facing artifacts.** Seven records (Day 21, 24, 25, 27, 28, 29, 30) are missing code for a *stated learning outcome* because the resource that would cite it belongs to a neighbouring day. The rule protects citation integrity at the cost of teachability.
2. **The corpus has no authoritative LO definition table.** Day 37 admits `course-catalog.json` contains none; Day 37, 38, 39-64 and 65-66 then each improvise a different reading of what LO10 and LO11 denote. The OJT evidence checklist and the final evaluator rubric are keyed to labels the course never fixed.

Rewrite distribution: **NONE 0 / LIGHT 17 / MEDIUM 17 / HEAVY 6**. No record needs to be discarded; the roadmap (15 units, 40 records, unit sequencing) is sound and is preserved throughout this audit. The six HEAVY records are all hands-on: Day 12, 15, 21, 30, 33, 34.

Verdict: **READY_FOR_CONTENT_IMPROVEMENT_PLAN**.

**Baseline:** Java 17 / Spring Boot 3.x / Spring Framework 6 / Jakarta. Vietnamese prose with English technical terms. Quoted material is reproduced verbatim from the source.

## Audit Method

**Scope:** all 40 records, read serially from a per-record dump of the authored JSON (sections, blocks, code, practices, commonMistakes, enhancedExercises, sourceUsage, references, `authoring.limitations`). Mechanical metrics were computed separately over the JSON corpus.

**Rubric (§5), 1–5 per dimension:**

| | Dimension | 1 | 5 |
|---|---|---|---|
| A | Concept clarity | term asserted | concept built from what the learner already has |
| B | Mental model | no model | one model that organises the whole lesson |
| C | Why / problem framing | "this is how you do it" | the problem is felt before the solution appears |
| D | Core mechanics | surface syntax | the mechanism that makes behaviour predictable |
| E | Example quality | none or broken | correct, minimal, then realistic |
| F | Edge cases | none | the cases that actually break in production |
| G | Common mistakes | generic | diagnostic, with the cause |
| H | Java→Spring connection | absent | the Spring feature is derived from the Java idea |
| I | Production relevance | academic | the reader could ship it |
| J | Internal coherence | parts contradict | prose, code and practices agree |
| K | Difficulty progression | flat or whiplash | load matches position in the course |
| L | Reference quality | uncited or wrongly cited | claims resolve to read sources |

**Kind-sensitivity (§3).** Records were judged against their own job, not against a single template:

- `theory` (20 records) — judged against the ideal theory shape in §6 below. This is where the rubric is fully in force.
- `lab` / `project` (16) — judged on whether the brief's deliverables have artifacts, whether acceptance criteria exist, and whether the reference code obeys the rules the course itself teaches. D/E/F are scored against the *assignment's* needs.
- `exam` (Day 37, 38) — judged as assessment scaffolds: scope, revision map, assessment shape. Teaching mechanics are not their job, so a low D is not automatically a defect.
- `ojt` (Day 39-64, one record for 26 days / 3960 min) and `evaluation` (Day 65-66, 600 min) — aggregate records. 26 days of external mentor-directed work cannot be authored as content; the correct deliverable is a self-operating framework, and they were judged as such.

**Length was explicitly not a quality signal (§7).** Day 07's Inner Classes section is long and is a definition dump; Day 31's `<important>` about the single `GlobalExceptionHandler` is three sentences and is one of the best blocks in the corpus.

**Flags used (§8–§15):** `DEFINITION_DUMP`, `TOY_ONLY` (a toy example that *progresses* to a realistic one is good and was not flagged), `SPRING_MAGIC`, `MISSING_BACKEND_CONNECTION`, `PREREQUISITE_GAP` (verified against the real `lesson-index.json` ordering, not assumed), `BAD_DUPLICATION` (distinguished from `GOOD_RECAP`: Day 14's scope recap is duplication because it restates Day 13 verbatim; Day 25's explicit unification of the proxy rule with Day 20 and Day 23 is a good recap), `SOLUTION_HANDED_OVER`, `INSUFFICIENT_FOR_PROJECT_APPLICATION`, `REFERENCE_GAP`.

**Limits of this audit, stated honestly:**

- No web research was performed (§16). The citation audit is source-internal: it compares `sourceUsage` locators and `references` against `content/source-notes/*.json` read status only. Where a resource is 404 or unread, that is recorded as a fact about the manifest, not as a judgement about whether the claim is true.
- No citation was repaired and no `lessonMap` was inspected for modification (§15). `INSUFFICIENT_FOR_PROJECT_APPLICATION` findings are about whether a lesson can support project work, not about the mapping.
- Compile status is taken from the authored `compile` field. 41 of 117 code blocks are compile-checked; the other 76 carry a `partialReason`. Every Java block from Day 13 onward is `compile=false` for one shared, legitimate reason: the pipeline's `javac --release 17` has no Spring/Jakarta jars on the classpath. That is a pipeline limitation, not a content defect, and was not scored against the lessons — but it does mean the Spring half's code is unverified, which is why the code defects listed below (Day 22's `SecurityConfig`, Day 19's `Product`/`ProductEntity` mismatch, Day 24's missing Hibernate imports) survived to publication.

### Pattern 1 — Assignment scaffolding collapses after Day 12, and never recovers

Day 03, Day 06 and Day 09 each carry an acceptance-examples table with hand-computed expected values. From Day 15 onward, **nine consecutive hands-on records have neither an acceptance table nor a rubric**: Day 15, 18, 21, 24, 27, 30, 33, 34, 35. Day 36 is the **only record in the entire corpus with a weighted rubric**; Day 38 has a flat self-rubric; Day 65-66 has an evaluator rubric with no level descriptors.

This is the single most consequential structural finding, because it means the learner cannot tell whether their work is correct for the entire Spring half and the entire capstone.

### Pattern 5 — Practices systematically under-test the lesson's own commonMistakes

The theory lessons identify traps well and then do not assess them. Practices are capped at 4 per record (schema allows 2–4), so a lesson with 11–15 mistakes cannot cover itself.

| Day | mistakes : practices | Day | mistakes : practices |
|---|---|---|---|
| 29 | **15 : 4** (worst) | 20 | 11 : 4 |
| 28 | 11 : 4 | 23 | 9 : 4 |
| 19 | 11 : 4 | 25 | 9 : 4 |
| 04 | 11 : 3 | 13 | 9 : 4 |
| 26 | 10 : 4 | 02 | 10 : 4 |

Corpus-wide: 66 multiple-choice practices, all 4-choice, **89% (59/66) have the correct answer as option (a)** — a pattern a learner will notice within a week and exploit. 57 practices have a `solution` field holding a bare choice id rather than an explanation.

Nine records share one specific shape — `prac-2`'s "solution" is a code block already printed in the body: Day 16, 22, 23, 25, 26, 28, 29, 30, 36.

The three weakest individual practices in the corpus: Day 30 `prac-4` (grades recall of the brief's own text, `su=[]`, hint "Nhớ lại đúng thứ tự được ghi trong đề bài Lab 10"), Day 37 `prac-3` (list the 7 section headings of the Spring Framework Reference in order), Day 29 `prac-4` (grades a literal property string).

### Pattern 6 — The capstone was authored to a fixed thin template

All eight non-theory records from Day 31 onward have **exactly 3 commonMistakes, exactly 4 practices and exactly 2 enhancedExercises** — Day 31, 32, 33, 34, 35, 36, 39-64, 65-66 — regardless of scheduled duration, which ranges from 150 minutes to 3960. Each also substitutes at least one bare `<template>` for a required deliverable. The scaffolding was sized to the template, not to the brief.

### Pattern 7 — One mental model is genuinely reused, and it is the course's best asset

The AOP proxy / self-invocation mechanism is taught once and then *reused* rather than re-explained: Day 20 (`@Transactional` self-invocation commits half-written data), Day 23 (`@PreAuthorize` has the same three limitations, derived from the same mechanism), Day 25 (explicitly unified — cache failure is "cùng bản chất với `@Transactional` … và `@PreAuthorize`"), Day 35 (mistake #2, `@Async` self-invocation). This is the strongest internal-coherence evidence in the course and the model the rest of the corpus should follow.

### Pattern 8 — No record has a closing synthesis section

Across all 40 records there is no "what you now know / what comes next" section. The only recap-titled section in the corpus is Day 14's "DI và Bean Scope (ôn lại)", and it duplicates Day 13 rather than synthesising it. Day 09's `SimpleHashMap`, Day 11's concurrency model and Day 16's DispatcherServlet model all end without being tied to what follows.

### Mechanical corpus profile

- **Citations: 919 markers, 579 unresolved (63.0%).** Worst: Day 15 82%, Day 16 78%, Day 17 78%, Day 36 76%, Day 20 75%, Day 34 75%, Day 19 74%. Best: **Day 37 17%**, Day 27 30%, Day 31 50%. Zero id collisions. Unused `sourceUsage` entries in Day 06, 09 (3), 12 (2), 15, 21, 35 (2).
- **Source availability:** Day 07 has only 1 of 5 resources readable, Day 10 2 of 5, Day 04 3 of 5, Day 32 2 of 4, Day 34 2 of 4, Day 33 3 of 5. Day 38, 39-64 and 65-66 have `resourceIds=[]` **by design** per `course-catalog.json`. Day 30 declares 7 `authoring.limitations` — the most in the corpus.
- **Duplication:** no gross prose overlap (max 6-gram similarity 4.3%, Day 17↔Day 18). But **Day 31 and Day 32 share the identical title "System Design & Project Kickoff"**; "Pham vi buoi hoc" is used as a section title 12 times; Day 06 and Day 09 share two section titles verbatim.
- **Orthography:** 28 of 197 section titles are diacritic-free, concentrated in Day 25 → Day 38.

### Depth profile

Judged as "is the depth right for this position in the course", not "is it long".

**Potentially too deep for the slot (5 records).** All are *good* content whose problem is load, not accuracy — the correct fix is redistribution, never deletion:

- **Day 11** (Concurrency & File I/O) — six major topics in 150 minutes: threads, atomicity, visibility, pools, NIO.2, serialization. Largest record in the corpus by block count (38). K=3.
- **Day 08** (Generics, Collections & Exceptions) — four large topics in one record, 33 blocks.
- **Day 23** — three unrelated subjects (method security, CORS/CSRF, N+1) in one "Guides/Review" day with no synthesis.
- **Day 29** — 15 commonMistakes plus five operability domains (OpenAPI, logging, MDC, health/metrics, Docker) in one record.
- **Day 07** — interface + nested types + enum + all five SOLID principles; SOLID gets one paragraph.

**Too shallow for the slot (11 records).** Depth is below what the record's own stated outcomes require:

- **Day 37** — one 5-row table as the revision map for 36 days; 2 commonMistakes.
- **Day 39-64** — 6 blocks for 3960 scheduled minutes; no technical layer at all.
- **Day 65-66** — 6 blocks for 600 minutes, 5 of them `<template>`.
- **Day 30** — 4 of 7 sections are a single `note`.
- **Day 12, 15, 21** — 3 of 5, 2 of 5 and 3 of 5 deliverables respectively have no artifact.
- **Day 31** — zero Java; the only code block is a `lang=text` directory tree.
- **Day 32** — the ERD, the record's headline artifact, is a bare `<template>`.
- **Day 33, 34** — 2 of 4 and 2 of 4 deliverables are one-sentence templates.

Within otherwise appropriate records, four sections are individually too shallow: Day 01's Arrays & varargs (two paragraphs, no code, no citation) and JRE/JDK (two definitions plus a table), Day 07's Inner Classes and Enums (code embedded inside prose sentences), and Day 25's `@Async`/`@Scheduled` (five and three prose blocks, no code, both stated outcomes).

**Appropriate (24 records).** The remaining theory corpus. Notably well-calibrated: Day 13 (six scopes with the singleton hazard and the pragmatic default), Day 16 (two-stage controller progression), Day 19 (persistence context before relationships before N+1), Day 26 (five subjects that genuinely share one boundary theme).

The overall shape is inverted relative to effort: the Java half is dense and occasionally overloaded, while the capstone — where the learner works longest and most independently — is the thinnest part of the course.

## Java → Spring Bridge

The course's design intent is that the Java half earns the Spring half. Where that intent is realised it is realised very well; the failures are concentrated in one place.

**Bridges that work (deliberate, mechanical, and cashed in later):**

| Java idea | Spring payoff | Where |
|---|---|---|
| Polymorphism → Strategy | "Dependency Injection chỉ là polymorphism cộng với việc chuyển quyền chọn implementation ra khỏi class sử dụng nó" — and "Lớp `Checkout` ở trên đã là một Spring bean đúng chuẩn dù chưa có annotation nào" | Day 05 → Day 13/14 |
| Shared heap, private stack | a singleton bean serves all request threads, so a mutable field in `@Service` is "bug đồng thời chờ xảy ra" — given as the *technical reason* the course insists on `final` fields and constructor injection | Day 11 → Day 13/14 |
| `int` vs wrapper | `Long` not `long` for an entity id, because a primitive cannot represent "not yet persisted" | Day 01 → Day 19 |
| `record` semantics | why a `record` **cannot** be a JPA entity (final fields, no no-arg constructor, no proxying) — correctly closing the loop on Day 04's record enthusiasm | Day 04 → Day 19 |
| Exception layering | infrastructure error → domain translation preserving cause → outermost layer decides presentation, named in advance as the shape of `@ControllerAdvice` | Day 08 → Day 17 |
| `enum` constants are load-time singletons | never persist `ordinal()`; use `@Enumerated(EnumType.STRING)` | Day 07 → Day 19 |
| `ThreadLocal` and thread affinity | `SecurityContextHolder` does not follow `@Async`; MDC does not either | Day 10/11 → Day 22 → Day 25 → Day 29 |
| `Optional<T>` | `Optional<T> findById(ID)` named as the canonical good use before the learner meets it | Day 10 → Day 19 |
| Path traversal via `normalize()`/`startsWith` | upload security | Day 11 → Day 26 |
| `groupingBy` + downstream | "bản Java của câu SQL `GROUP BY ... COUNT(*)`" | Day 10 |
| AOP proxy | one mechanism, four applications (`@Transactional`, `@PreAuthorize`, `@Cacheable`, `@Async`) | Day 20 → 23 → 25 → 35 |

**The one broken bridge, and it is expensive.** Day 09's Lab 3 has the learner design a class named `DataAccessException` with subclasses for duplicate-key and not-found. That is, name for name, `org.springframework.dao.DataAccessException` / `DuplicateKeyException` / `EmptyResultDataAccessException`. Spring's translation of `SQLException` into exactly that hierarchy — via `@Repository` — is the payoff, and it is mentioned neither in Day 09 nor forward-linked to Day 19/20. Day 13 later explains `@Repository` exception translation properly, but never says "you already built this". The single best available bridge in the Java half is left unbuilt. `MISSING_BACKEND_CONNECTION`, Day 09.

**The absent bridge: SQL.** The course teaches JPA (Day 19–21), writes JPQL and native queries (Day 20), warns about N+1 and JOIN FETCH Cartesian products (Day 19/23), asks for a 7-table ERD (Day 32) and for search/filter/pagination (Day 34) — and teaches **no SQL, no JOIN semantics and no indexing anywhere**. Day 10's `groupingBy`→`GROUP BY` remark is the only place the corpus connects Java to relational thinking. The learner is asked to reason about query plans they have never been shown.

**Prerequisite inversions (§12), verified against `lesson-index.json` ordering:**

| Used at | Taught at |
|---|---|
| Day 05 — `interface`/`implements`, default-method conflict resolution (the whole `DiscountPolicy` example) | Day 07 |
| Day 05 — `try`/`catch` (`CastDemo`), generics (`List<Vehicle>` in exercises) | Day 08 |
| Day 06 — `List<Employee>`, `.stream().map()`, lambdas in the reference solution | Day 08 / Day 10 |
| Day 07 — the flagship `Validator<T>` example uses generics and lambdas | Day 08 / Day 10 |
| Day 13 — `@RestController` in examples | Day 16 |
| Day 14 — `@Valid`, `RestClient` | Day 17 / Day 26 |
| Day 19 — `@Transactional`, N+1 cure detail | Day 20 |
| Day 21 — `@DataJpaTest` | Day 28 |
| Day 24 — Redis, `@SpringBootTest` | Day 25 / Day 28 |
| Day 26 — `MockMvc` | Day 28 |

Most of these are mild forward references. **One is a hard defect:** Day 19's `PREREQUISITES` field states "Đã hoàn thành Unit 6 (Spring Data JPA cơ bản: Repository, @Query, kết nối database)" — but Unit 6 is Spring MVC/REST, and `Repository`/`@Query` are first taught at Day 20, *after* Day 19. A learner checking their prerequisites concludes they missed a unit that does not exist.

## Unit Analysis

All 15 units, in `lesson-index.json` order. "Mean" is the mean of the unit's records' A–L means.

### Unit 01 — Java foundations (Day 01, 02, 03) — mean 3.53
Installs the execution model and the imperative core. Both theory records are solid on mechanics (JIT warm-up as an observable phenomenon; numeric promotion taught through the failing case `long total = intA * intB`) and both under-test them: 6 of Day 02's 10 commonMistakes have no practice, and 3 of its 4 practices are about `switch`. Day 03 hands over its own deliverable — the complete `StringCalculator.calculate` including the error path is printed, and `prac-1` names that block as its solution. Day 02 contains the corpus's only outright non-compiling snippet presented as correct: `numbers.stream().filter(n -> n % 2 == 0).sum()` does not compile in either reading, and it is the first Stream code the learner sees. Day 01's Arrays & varargs section is two paragraphs with no code and no source. **Unit verdict: strong mechanics, weak assessment, one broken snippet, one handed-over lab.**

### Unit 02 — Object model (Day 04, 05, 06) — mean 3.78
The strongest conceptual unit in the Java half. Day 04's five-step mechanics of `new Book(...)` and its reframing of encapsulation away from getter/setter ritual ("người dùng class này cần *làm* gì") are excellent; Day 05's Strategy→DI section is the best Java→Spring bridge in the course. Both are damaged by the same two defects: practices far below the material (Day 04 has 3 practices for 11 mistakes, 2 of them recall trivia), and prerequisite inversion — Day 05 depends on interfaces (Day 07), try/catch (Day 08) and generics (Day 08) with no signpost that they are previews. Day 06 publishes its entire 68-line deliverable, requires three unlearned concepts to read it, and computes payroll in `double` five days after Day 01 forbade it. **Unit verdict: best concepts, worst prerequisite discipline.**

### Unit 03 — Contracts and API literacy (Day 07, 08, 09) — mean 3.75
Day 08 is the Java half's second-best record (erasure used to derive every generics restriction at once; the equals/hashCode contract taught via the unreachable-entry consequence; try-with-resources reaching `getSuppressed()`). Day 07 carries the corpus's most honest source-gap handling — 4 of 5 resources 404, one `sourceUsage` total, disclosed in three `authoring.limitations` and again in-body at three section heads — but its Inner Classes and Enums sections are definition dumps with code embedded inside prose sentences. Day 09 is where the unit's cost shows: a 131-line reference implementation *is* the deliverable, and the `DataAccessException` bridge to Spring is left unbuilt. Both Day 08 and Day 09 also require a coverage tool the course never names. **Unit verdict: excellent theory, a lab that answers itself and misses its own payoff.**

### Unit 04 — Functional style and shared state (Day 10, 11, 12) — mean 3.83
Highest-scoring unit in the Java half, and the widest internal spread (Day 11 at 4.58, Day 12 at 2.58). Day 10's stream-fusion explanation and parallel-stream production warnings are excellent, but its commonMistake #1 contradicts its own body (telling the learner to call `isPresent()` before `get()` while the body calls that "chỉ viết lại `if (x != null)` bằng cú pháp dài hơn"), and three of five sections ship `lang=text compile=false` code. Day 11 is the corpus's best record. Day 12 then breaks three of the unit's own rules in one file: it collects 500K rows after opening a lazy stream (contradicting its own mistake #1), omits the charset Day 11 mandated, and sums revenue in `double`. **Unit verdict: the peak and the trough of the Java half in one unit.**

### Unit 05 — Spring Boot core (Day 13, 14, 15) — mean 3.69
The pivot. Day 13 installs the container vocabulary well — eager singleton instantiation argued as fail-fast ("sai cấu hình thì ứng dụng không lên, thay vì chết giữa giờ cao điểm"), scope mixing explained by *why* the dependency resolves once — but three of its five topics have no source at all, and `@PostConstruct`/`@PreDestroy` ordering is a stated outcome with no code. **Role:** the API-literacy lesson — type parameters, the collection contracts, and the error model. Everything from Day 13 onward consumes these three.
**Kind:** theory (unit-03). **Scores:** A5 B5 C5 D5 E4 F5 G5 H5 I5 J3 K3 L2 — **mean 4.33**

## Reference & Citation Audit

This section is **source-internal**: no external URL was fetched, no citation was corrected, and no claim below rests on web research (§16, §5 L). Everything here is derived from `content/source-manifest.json`, `content/source-notes/*.json`, the `sourceUsage[]` / `references[]` arrays of the 40 authored lessons, and the gate logic in `tools/build_site.py` and `tools/validate_lessons.py`.

### How citation works in this corpus

A content block carries `citations[]` whose entries point at `sourceUsage[].id`. A marker renders as a clickable footnote **only if** that same id is also published as a `references[].citationId`. Otherwise it renders as `[?]` — reproduced as `[?dayXX-src-N]` in the audit dumps. Two build gates decide whether an id can be published:

1. `_citation_locator_matches()` requires the `sourceUsage.locator` (written as `§heading`) to match a heading actually recorded in the resource's read notes.
2. `_slim_authored_lesson()` refuses any reference whose resource has `read.status != "read"`.

Both gates are correct as engineering. Their combined effect on the learner is not.

### The headline number

**919 citation markers across the corpus; 579 unresolved — 63.0%.** Nearly two out of three citation markers a learner meets render as `[?]` rather than as a usable reference.

The distribution is the diagnostic, not the average:

| Extreme | Record | Unresolved | Why |
| --- | --- | --- | --- |
| Best | Day 37 | **17%** | The day's own `resourceIds` (JLS 17, Spring Boot reference, Spring Framework reference) are exactly what a revision map cites. |
| Best | Day 27 | **30%** | Every resource the assignment needs sits in its own `resourceIds`. |
| Best | Day 31 | 50% | Little technical content, so little to cite. |

Day 27 and Day 37 are the control group. When a record's required resources happen to sit in its own `resourceIds`, citation health is excellent with no change in authoring effort. **That makes the diagnosis structural, not a sourcing failure or an authoring lapse.**

### The dominant structural cause: the no-cross-lesson-citation-borrowing rule

A lesson may only cite resources listed in its own `resourceIds`. A resource read for Day 19 cannot be cited by Day 21 even though Day 21 teaches the topic it covers. Because `course-catalog.json` assigns resources per catalog row and the teaching order does not track that assignment, the rule systematically strands material. Seven confirmed instances, each producing a stated learning outcome with **no code block and no citable support**:

| Record | Topic taught with no artifact | Resource lives at |
| --- | --- | --- |
| Day 21 | cascade / fetch strategy | Day 19 |
| Day 24 | Method Security (`@PreAuthorize`), `@WithMockUser` | Day 23 |
| Day 25 | `@Async`, `@Scheduled` | Day 27 |
| Day 27 | CSV export | Day 26 |
| Day 28 | Testcontainers | Day 29 |
| Day 29 | Docker | Day 30 |
| Day 30 | structured logging, Actuator / `HealthIndicator` | Day 29 |

This is the single highest-leverage finding in the audit. The rule protects citation integrity and it is the direct cause of the corpus's most visible content defects: Day 25 explains `@Async` in five prose blocks and shows none of `@EnableAsync`, an executor bean, or `AsyncUncaughtExceptionHandler`; Day 24 reduces two of five brief deliverables to a single `note` each; Day 21 teaches cascade behaviour with nothing a learner can run. **The learner-facing cost is being paid to preserve a metadata invariant.**

The remedy is not to weaken the invariant. It is to permit an uncited-but-disclosed code block — the mechanism `authoring.limitations` already provides and which Day 15, Day 26 and Day 38 already use well for genuine source gaps. A block labelled "derived from Day 23's verified content" is honest; an absent block is not.

### Internal references

Internal references (`references[].internal` with a `description` instead of a `citationId`) are not subject to either gate, and they are largely accurate. Three are wrong-target, and the pattern in the failures is precise:

| Reference | Claims | Reality |
| --- | --- | --- |
| `day38-ref-3` | Day 36 details `@DataJpaTest` / `@WebMvcTest` / Testcontainers | **Day 28** teaches them; Day 36 only re-explains them |
| `day30-ref-6` | Day 36 as the source for its testing material | same inversion |
| `day6566-ref-2` | Day 36 for defense structure | **correct** — Day 36 originates this |

**Internal-reference accuracy tracks whether the target *originates* the material.** Two of the three wrong-target references point at Day 36, the corpus's largest recap, which is exactly what a heavy duplication site does to a reference graph: it becomes a plausible-looking citation target for material it never taught. Fixing Day 36's duplication (see the Priority Matrix) removes the cause rather than the symptom.

### Reference quality where it works

L scored 4–5 in a minority of records, and the reasons are worth preserving as the model:

- **Day 37 (L=4)** — 5 external references, all publishing, and the two series-landing-page resources are explicitly disclosed as tables of contents "không phải nguồn trích dẫn kỹ thuật chi tiết".
- **Day 27 (L=5)** — 7 external references, 7 of 10 markers resolving.
- **Day 26 (L=4)** — all six references publish, and the Excel gap is disclosed as a corpus-wide source gap rather than filled with invented guidance.
- **Day 15, Day 38, Day 39-64, Day 65-66** — `resourceIds=[]` or a genuine gap, each disclosed in `authoring.limitations` with the reason. `resourceIds=[]` at Day 38 / 39-64 / 65-66 is by catalog design, correctly stated, and is **not** counted as a citation defect anywhere in this audit.

The corpus's disclosure discipline is consistently good. Its citation *resolution* is consistently poor. Those are separate problems and only the second is structural.

### Limits of this section

No external source was fetched, so no claim is made about whether any cited document still says what the read notes record. Locator drift — a resource whose headings have changed since the notes were taken — is therefore undetectable here and should be checked before any citation repair is attempted.

## Practice / Assignment Alignment

The course's stated preference (§14) is **problem + constraints + hints, not full code**. Measured against that preference, the practice layer is the corpus's most mechanically defective component — and the defects are systematic rather than distributed, which makes them cheap to fix.

### The schema cap

`practices` is bounded at 2..4 entries. That cap is the direct arithmetic reason the practice layer cannot cover the mistake lists it sits beside:

| Record | commonMistakes | practices | Coverage |
| --- | --- | --- | --- |
| Day 29 | 15 | 4 | worst in corpus |
| Day 26 | 10 | 4 | mistakes #1/#4 and #3/#10 are duplicates, so 8 distinct against 4 |
| Day 25 | 9 | 4 | #7/#8/#9 (async `void` handler, entity across threads, multi-instance scheduling) have no matching practice |
| Day 28 | 11 | 4 | — |

This is not an authoring failure. Where a record has 9–15 well-chosen mistakes and 4 practice slots, the mistakes are the asset and the cap is the constraint. The fix is either to raise the cap or to add a lightweight self-check block type that is not a `practice` — a decision that belongs in the improvement plan, not in an audit.

### Two mechanical defects that need no judgement

**89% of multiple-choice answers are option (a) — 59 of 66.** A learner who never reads a question and always picks (a) scores 89% on the corpus's entire MCQ layer. This invalidates the multiple-choice interaction as an assessment instrument, and it is a pure generation artifact: shuffling the option order changes no content and repairs it completely. It is the single cheapest high-value fix in the audit.

**57 solutions are a bare choice id.** A solution field reading `b` teaches nothing about why the other three options fail, and the distractors in this corpus are usually the *good* part of the item — Day 38's `prac-1` distractor (d) "create a new `GlobalExceptionHandler` just for this feature" is the exact mistake Day 31 was written to prevent, and the solution field never says so. Every bare-id solution is a discarded teaching opportunity that the item's own author had already set up.

### What the practices test versus what the record taught

The recurring misalignment is that practices grade the *most recallable* fact rather than the most transferable idea:

- **Day 37** — 3 of 4 practices grade the structure of the reference documentation (JLS 17's scope, Spring Boot's three goals, "list the 7 parts of the Spring Framework Reference in order"). None touches a technical idea from Day 01–36, on the eve of the theory exam.
- **Day 25** — `prac-3` grades that `GETEX` requires Redis 6.2.0, the least transferable fact in a record whose best material is cache-key design, stampede/penetration, and eviction-versus-transaction. None of those three is tested.
- **Day 26** — `prac-2` is a method-signature recall; the two highest-value ideas in the record (the time-budget discipline, retry nested inside the breaker) go untested, and nothing tests download/streaming, IDOR, or `WebClient` timeouts.
- **Day 39-64 / Day 65-66** — all eight practices are writing prompts about the record's own templates; only `prac-4` in each has a determinate answer.

### `SOLUTION_HANDED_OVER`

A recurring shape: `prac-2` returns a short copy of a pattern the record already printed. Confirmed at Day 16, Day 22, Day 23 and Day 25 — a two-line `@CacheEvict(allEntries = true)` method at Day 25, structurally identical to its predecessors. Individually minor; as a repeated template it means one of four practice slots is spent on transcription in a quarter of the Spring half.

### Where alignment is good

- **Day 24 `prac-4`** grades the `@SoftDelete` + `@NotFound(action = IGNORE)` interaction on a `@ManyToOne LAZY` — a genuinely non-obvious production behaviour, tested exactly where it was taught.
- **Day 27 `prac-1`** grades the *reasoning* behind evicting all entries (list caches are keyed by page and filter, so computing affected keys costs more than it saves) rather than the annotation name.
- **Day 38 `prac-1`** tests architectural consistency — where does a new `CouponExpiredException` belong — with distractors drawn from real learner behaviour, and `prac-3` routes an async requirement back to Day 35's `@Async` rather than inviting a new pattern.
- **Day 24 `prac-3`** tests the *dependency* between `batch_size` and `order_inserts`/`order_updates` instead of the setting names.
- **Day 39-64 `prac-4`** requires escalation to carry evidence of what was already tried, with "wait for the next scheduled check-in" as the distractor.

Every one of these grades a decision rather than a token. They are the pattern the rest of the practice layer should be regenerated against.

### Assignment / lab alignment

The larger alignment failure is not in `practices` but in the hands-on records' briefs: **nine consecutive hands-on records state deliverables with no acceptance criteria** (Day 15, 18, 21, 24, 27, 30, 33, 34, 35), and **twelve deliverables across ten records have no artifact at all**. Day 03, Day 06 and Day 09 had acceptance tables; the scaffolding was dropped after Unit 3 and never restored. A brief that lists five deliverables, provides code for two, and states no acceptance criterion for any is not assessable by the learner or the mentor — see Project Application Readiness below.

## Recommended Rewrite Order

Six waves, ordered so that every structural decision is made before any lesson that depends on it is rewritten, and so that the cheapest high-value fixes land first. Rewriting Day 21 before deciding the citation-borrowing question, or Day 36 before the LO table exists, would mean rewriting them twice.

### Wave 0 — Structural decisions (no lesson rewritten)

These are three decisions plus one pipeline change. Nothing else should start until they are settled, because items in later waves resolve differently depending on the answers.

1. **Decide the citation-borrowing question** (matrix item 11). Recommended: permit an uncited code block when it is disclosed in `authoring.limitations` as derived from a named sibling record — the mechanism Day 15, 26 and 38 already use well. 2. **Write one authoritative LO definition table** (item 12) and make Day 37, 38, 39-64 and 65-66 cite it. Without this, Day 39-64's evidence checklist and Day 65-66's evaluator rubric cannot both be correct.

## Rewrite Guardrails

Constraints any Content Improvement Plan must respect. These are derived from the audit, not invented for it.

**Preserve the roadmap.** The instruction is GIỮ SƯỜN + NÂNG CHẤT LƯỢNG NỘI DUNG: 40 lessons, 15 units, groups java=12 / spring=24 / completion=4, and `EXPECTED_LESSON_IDS = day-01..day-38 + day-39-64 + day-65-66`. No record may be split, merged, reordered or renumbered. Where this audit recommends new material (SQL/index, `@Version`/`@Lock`), it must fit inside an existing record's sections, not become a new day.

**Do not modify the approved tracks.** Build While You Learn, the Spendwise project track, the web UI, `index.template.html`, `index.html`, the Spendwise JSON and the build scripts and tests are FINAL_APPROVED at `8a0debc` and `9cd0424`. `lessonMap` is read-only. Where a course record's brief depends on untaught content, fix the record, not the project track.

**`index.html` is a build artifact.** All edits go to `content/lessons/*.json`; the site is regenerated by `tools/build_site.py`. Never hand-edit the generated HTML.

**Respect the schema.** Lesson schema v1 uses closed-key objects; block types are `paragraph|note|important|warning|code|table|deliverable|template`; `kind` is `theory|lab|project|exam|ojt|evaluation`; practice `type` is `concept|predict-output|coding|applied` with `interaction` of `self-check|multiple-choice`; `practices` is bounded 2..4. Two audit findings (items 22 and 24) are constrained by that cap — if the plan intends to fix mistake-coverage, the cap must be raised or a new non-`practice` self-check block added deliberately, as a schema decision with its validator and build-gate consequences worked out, not as an incidental edit.

**Keep the baseline.** Java 17, Spring Boot 3.x, Spring Framework 6, Jakarta. Java 17 has no virtual threads and Day 25 correctly says so; nothing may quietly assume a later baseline.

**Keep the language contract.** Vietnamese prose with English technical terms, matching the existing corpus.

**Disclosure over silence.** Where content cannot be sourced, say so in `authoring.limitations` with the reason, as Day 15, 26, 27, 38, 39-64 and 65-66 already do. An honest gap is a feature of this corpus and must survive the rewrite. Conversely, an *undisclosed* gap is the defect: Day 38's false capstone premise is severe precisely because nothing states it.

**Never invent authority.** Day 39-64 refuses to describe FSU Project conventions the syllabus does not supply, and Day 65-66 refuses to invent an official grading scale. Both refusals are correct and both must be preserved. New rubrics and scales must be labelled as suggestions unless an authoritative source exists.

**Do not weaken the citation gates.** `_citation_locator_matches()` and the `read.status == "read"` requirement are correct engineering. The recommended remedy is a disclosed uncited block, not a relaxed gate. And no citation should be repaired without first checking for locator drift — this audit fetched nothing external and therefore cannot confirm that any cited document still contains the heading its read notes record.

**Verify code before publishing it.** Three of the corpus's concrete defects exist because `compile=False` from Day 13 onward made verification impossible. Any rewrite that adds or changes Java should not be considered done until the sample compiles against a classpath that includes Spring and Jakarta.

**Length is not the target.** Per §7 this audit did not score length, and the rewrite must not either. Day 36 is the largest record in the corpus and one of the most duplicative; Day 37 is among the smallest and the best-cited. The goal is a record that teaches — Concept → Mental Model → Problem/Why → Core Mechanics → Simple Example → Realistic Example → Edge Cases → Common Mistakes → Connection forward — not a longer record.

**Toy → realistic is the desired shape.** A simple example followed by a realistic one is good and must not be flagged or removed; `TOY_ONLY` applies only where the toy example is the *only* example.

**Fix causes, not symptoms.** Three findings are single decisions that resolve many records: the citation-borrowing rule (7 records), the LO definition table (4 records), the missing SQL foundation (the whole JPA half). Rewriting individual lessons before these are settled means rewriting them twice.

## Verdict

The corpus has a clear, well-founded skeleton and a strong theory half (20 theory records, mean 4.23), a distinctly weaker hands-on half (16 records, mean 3.08) and a weak terminal band (4 records, mean 2.77). All 40 records have been audited with per-record scores, flags, rewrite levels and prioritised actions; the failures cluster into a small number of structural causes — the no-cross-lesson-citation-borrowing rule, the absent LO definition table, the absent SQL foundation, the dropped acceptance-criteria scaffolding, and a pipeline that could not compile Spring-era code — each of which is actionable without disturbing the roadmap or the approved tracks. No record requires deletion and none requires renumbering; rewrite levels are NONE 0 / LIGHT 17 / MEDIUM 17 / HEAVY 6.
